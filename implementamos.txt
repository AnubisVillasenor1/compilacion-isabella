ATLAS TRASCENDENCE
Propuesta final de descripción, alcance y funcionalidad
ATLAS Trascendence es un ecosistema digital soberano para la preservación, organización, federación y explotación inteligente del conocimiento. No es una aplicación aislada ni un frontend con documentación decorativa: es una arquitectura viva concebida para unir memoria institucional, identidad, publicación académica, observabilidad operacional, federación de sistemas y asistencia cognitiva dentro de una misma base conceptual y técnica.
Su propósito es convertir información dispersa en conocimiento estructurado, trazable y reutilizable. Para ello, ATLAS integra documentos, eventos, identidades, relaciones, versiones, auditorías y publicaciones en un modelo federado que permite operar con integridad, reproducibilidad y control. El sistema no sólo almacena contenido; lo interpreta, lo vincula, lo valida y lo prepara para ser publicado, sincronizado, auditado y reutilizado por otros nodos del ecosistema TAMV.
Naturaleza del sistema
ATLAS funciona como una plataforma de conocimiento y operación de nueva generación. Su diseño asume que la realidad institucional no puede resolverse con un repositorio simple ni con una interfaz bonita: requiere capas separadas de identidad, contenido, federación, publicación, seguridad, observabilidad y gobierno semántico. Por eso, el sistema se organiza como una arquitectura modular, event-driven, API-first, observable y federada.
El proyecto incorpora una lógica de crecimiento progresivo. En su núcleo hay un registro canónico de documentos y entidades; alrededor de ese núcleo orbitan servicios de identidad, publicación, conexión con federados externos, trazabilidad, auditoría, análisis semántico, y eventualmente inteligencia asistida por IA. El objetivo no es sólo “hacer software”, sino construir un medio durable para producir, preservar y distribuir conocimiento con control y continuidad.
Qué hace ATLAS
ATLAS realiza varias funciones simultáneas:
Registra y normaliza documentos, manifiestos, compendios y activos de conocimiento.
Vincula identidades institucionales y académicas como ORCID, GitHub y repositorios externos.
Versiona contenido y conserva un historial verificable de cambios.
Publica resultados hacia nodos federados como Zenodo, Figshare, OpenAIRE y GitHub.
Mantiene auditoría completa de eventos, accesos, modificaciones y sincronizaciones.
Observa la salud del sistema mediante métricas, logs, trazas y alertas.
Aplica reglas de gobernanza y validación para evitar divergencia arquitectónica.
Expone el conocimiento de forma navegable, reutilizable y extensible.
En términos prácticos, ATLAS actúa como un puente entre memoria, publicación, identidad y federación. Un documento no queda encerrado en un archivo: se convierte en una entidad viva con autoría, versión, relación semántica, trazabilidad y posibilidad de anclaje en múltiples sistemas.
Cómo lo hace
La lógica del sistema se apoya en una arquitectura distribuida y controlada. El usuario interactúa con una interfaz limpia; esa interfaz llama a un punto de entrada controlado; el punto de entrada valida identidad, permisos y formato; luego enruta la operación hacia servicios especializados. Cada servicio resuelve un dominio concreto: documentos, identidades, publicaciones, eventos, auditoría, seguridad o telemetría.
El corazón operativo es el flujo de eventos. Cuando ocurre una acción importante —crear un documento, vincular una identidad, solicitar una publicación, reservar un DOI o sincronizar un federado— el sistema genera un evento. Ese evento se conserva, se audita y puede activar automatizaciones o workflows. Así, ATLAS no depende de lógica dispersa e incontrolable, sino de procesos trazables y repetibles.
Este enfoque permite que el sistema crezca sin perder forma. La federación no se implementa como acoplamiento directo entre piezas, sino como contratos bien definidos, adaptadores desacoplados y políticas de sincronización. Cada federado externo se trata como interoperable pero no confiable por defecto, con validaciones, reintentos, límites de tasa y mecanismos de recuperación.
Capacidades principales
ATLAS incorpora capacidades que lo distinguen de un sistema documental convencional:
Memoria canónica estructurada.
Ingesta de conocimiento y clasificación semántica.
Publicación académica y científica.
Vinculación con identidades federadas.
Auditoría de eventos y cambios.
Observabilidad integral.
Gobernanza constitucional.
Arquitectura modular con límites claros.
Preparación para IA contextual y asistente cognitivo.
Interoperabilidad con sistemas académicos y de investigación.
Además, el sistema está diseñado para crecer hacia un modelo de federaciones funcionales donde cada dominio tiene autonomía relativa pero comparte principios, contratos y trazabilidad con el resto.
Inyección de capacidades, funciones, filtros y programas
La propuesta final de ATLAS no debe describirse como una suma de módulos aislados, sino como una red coordinada de capacidades. En esa red se integran:
Filtros de validación de contenido.
Filtros de seguridad y autorización.
Filtros de consistencia semántica.
Filtros de integridad documental.
Filtros de compatibilidad entre federados.
Filtros de publicación según estado y permisos.
Filtros de observabilidad para no saturar el sistema con ruido.
Filtros de gobernanza para evitar cambios no autorizados o no alineados.
Los programas actuales del TAMV se interpretan como capacidades activas del ecosistema, no como herramientas sueltas. En ese sentido, ATLAS integra programas de identidad, memoria, publicación, observabilidad, seguridad, coordinación y federación como parte de un mismo organismo digital.
Interconexión de datos y federaciones
El sistema se basa en la idea de que todo dato relevante debe poder relacionarse con otro dato relevante. Un documento puede estar vinculado a una identidad, una versión, una publicación, un evento, una federación, un anclaje y una auditoría. Esa interconexión permite construir grafo de conocimiento, trazabilidad institucional y memoria histórica del ecosistema.
Las federaciones funcionan como dominios con propósito propio. No son copias del mismo servicio, sino territorios conceptuales y funcionales que colaboran bajo reglas comunes. Así, ATLAS puede sostener una visión de identidad, conocimiento, seguridad, infraestructura e inteligencia sin perder consistencia estructural.
Seguridad y confiabilidad
ATLAS asume un modelo de seguridad fuerte desde su concepción. La seguridad no es un añadido posterior, sino parte de la forma en que el sistema piensa y actúa. El diseño presupone validación de entrada, autenticación federada, control fino de permisos, firma de eventos, auditoría completa y separación entre dominios internos y externos.
La meta es que cada operación relevante deje evidencia verificable y que ningún componente sensible dependa de confianza implícita. Esto es esencial para un sistema que aspira a preservar conocimiento institucional y operar como infraestructura duradera.
Visión de largo plazo
ATLAS Trascendence está concebido para durar, no sólo para funcionar. Su finalidad es crear una base técnica, documental y semántica que permita a una comunidad, institución o ecosistema construir sobre ella sin perder orden ni memoria. Por eso su valor no está únicamente en el código, sino en su capacidad de mantener contexto, historia, relaciones y propósito.
Si el sistema se implementa con disciplina, puede evolucionar hacia una plataforma de conocimiento soberano, publicación federada y asistencia cognitiva de alcance institucional y global. Su mayor fortaleza no es una sola función, sino la convergencia de varias capas bien diseñadas en un mismo marco operativo.
Cierre editorial
ATLAS Trascendence nace de una necesidad real: evitar que el conocimiento se fragmente, se pierda o quede atrapado en herramientas aisladas. En lugar de eso, propone una estructura que preserve, conecte, valide y proyecte la información hacia múltiples destinos, con trazabilidad y gobernanza.
Este compendio, este manifiesto y este sistema son parte de la misma intención: construir una infraestructura de conocimiento que no dependa de modas, sino de arquitectura, evidencia y continuidad.

3. Identidad canónica de documentos
3.1. Esquema document_uid
text
ATLAS-DOC-{federation}-{namespace}-{ULID}-{hash_prefix}
Ejemplo:
text
ATLAS-DOC-F2-KNOW-01J4R0ZP9V-8f3a1c2d
federation: F1–F7 (origen conceptual).
namespace: dominio lógico (KNOW, GOV, SEC, OBS, IA, etc.).
ULID: orden temporal monotónico.
hash_prefix: primeros bytes del hash SHA 256 del contenido canonicalizado.
3.2. Canonicalización y hash (pseudo código)
ts
function canonicalizeDocument(doc: DocumentInput): CanonicalDocument {
const normalized = {
title: doc.title.trim(),
content: normalizeWhitespace(doc.content),
metadata: sortKeys(doc.metadata ?? {}),
namespace: doc.namespace.toUpperCase(),
};
return normalized;
}

function hashCanonicalDocument(cdoc: CanonicalDocument): string {
const payload = JSON.stringify(cdoc);
return sha256(payload);
}

9. Flujo operativo end to end (ejemplo completo)
Usuario autenticado via ORCID.
identity-service crea/vincula atlas_identity_id y emite identity.linked.
Usuario crea documento.
document-registry-service:
canonicaliza contenido,
calcula hash,
genera document_uid,
guarda en Postgres,
emite documents.created.
publication-service consume documents.created y, según reglas, prepara publications.requested o espera acción explícita.
Usuario pulsa “Publicar”. BFF manda POST /v1/publications.
publication-service:
valida estado del documento,
reserva DOI en Zenodo → publications.doi_reserved,
crea release en GitHub, datasets en Figshare/OpenAIRE cuando corresponda,
emite publications.completed.
federation-anchor-service:
consume eventos de publicación,
genera lote de hashes por federado (F1–F7),
emite federations.anchored.
telemetry-service:
registra métricas, logs y traces de todo el flujo,
controla SLOs y dispara alertas si hay degradación.
security-core:
firma eventos críticos,
observa anomalías,
levanta incidentes si detecta patrones de riesgo.

4.3. Policy Rego (infra/opa-policies/publication.rego)
text
package atlas.publication

default allow = false
default reason = "policy_denied"

# Regla principal
allow {
allowed_state
allowed_federation
not high_risk_block
}

reason := msg {
high_risk_block
msg := "high risk document in restricted federation"
}

# Sólo documentos validados o ya publicados pueden ir a Zenodo
allowed_state {
input.action == "publish"
input.provider == "zenodo"
input.document.state == "validated"
} else {
input.action == "publish"
input.provider == "zenodo"
input.document.state == "published"
}

# Federaciones permitidas para publicación estándar
allowed_federation {
# Conocimiento general
input.document.federation_id == "F2"
} else {
# Otros federados, pero no estrictamente de seguridad crítica
input.document.federation_id != "F5"
}

# Bloqueo de alto riesgo en F5 salvo roles especiales
high_risk_block {
input.document.federation_id == "F5"
input.document.risk_level == "high"
not exception_role
}

# Excepción: roles con permisos explícitos
exception_role {
some r
r := input.actor.roles[_]
r == "security_admin"
}

src/domain/service.ts (trozo clave):

ts
import { getDb } from "../infra/db";
import { publishEvent } from "../infra/eventBus";
import { canonicalizeDocument, hashCanonicalDocument } from "./validators";

export async function createDocument(input: {
title: string;
content: string;
namespace: string;
federationId: string;
createdBy: string;
}) {
const db = getDb();
const canonical = canonicalizeDocument(input);
const hash = hashCanonicalDocument(canonical);
const documentUid = generateDocumentUid(input.federationId, input.namespace, hash);

await db.query("BEGIN");

await db.query(
`INSERT INTO documents
(document_uid, federation_id, namespace, title, state, current_version, created_by)
VALUES ($1,$2,$3,$4,'draft',1,$5)`,
[documentUid, input.federationId, input.namespace, input.title, input.createdBy]
);

await db.query(
`INSERT INTO document_versions
(document_uid, version, content, metadata, canonical_hash)
VALUES ($1,1,$2,$3,$4)`,
[documentUid, input.content, JSON.stringify(canonical.metadata ?? {}), hash]
);

await db.query(
`INSERT INTO events
(event_id, event_type, document_uid, federation_id, payload, hash_after)
VALUES ($1,$2,$3,$4,$5,$6)`,
[
generateUlid(),
"documents.created",
documentUid,
input.federationId,
canonical,
hash
]
);

await db.query("COMMIT");

await publishEvent("documents.created", {
document_uid: documentUid,
federation_id: input.federationId,
namespace: input.namespace,
title: input.title,
created_by: input.createdBy,
version: 1,
canonical_hash: hash
});

return { documentUid, hash };
}

import { FastifyRequest, FastifyReply } from "fastify";
import { createDocument } from "../../domain/service";

type CreateDocumentBody = {
title: string;
content: string;
namespace: string;
federationId?: string;
};

export async function createDocumentHandler(
request: FastifyRequest<{ Body: CreateDocumentBody }>,
reply: FastifyReply
) {
const { title, content, namespace, federationId } = request.body;
const actorId = request.user.sub; // asumimos user inyectado por authMiddleware

const fed = federationId ?? "F2";

const result = await createDocument({
title,
content,
namespace,
federationId: fed,
createdBy: actorId
});

return reply.code(201).send({
document_uid: result.documentUid,
canonical_hash: result.hash
});
}

package atlas.rbac.publication

default allow = false
default reason = "denied"

# Entrada esperada:
# input.action -> "publish"
# input.provider -> "zenodo" | "figshare" | ...
# input.jwt.claims -> OIDC claims

allowed_state

has_basic_scope {
some s

s == "documents:publish"
}

# Aislamiento multi-tenant
tenant_matches {
input.jwt.claims.tenant_id == input.document.tenant_id
}

# Sólo validated/published

input.document.state == "validated"

input.document.state == "published"

input.document.federation_id == "F5" # seguridad

not is_security_admin
}

some r

r == "security_admin"

1. Cinco servicios completos (visión implementable)
Voy a asumir stack Node.js + TypeScript + Fastify, NATS como bus de eventos y PostgreSQL como canon. HashiCorp Vault como secret store.
1.1. identity-service
Responsabilidad: identidad federada (ORCID, GitHub, etc.) y emisión de atlas_identity_id.
Endpoints:
•	POST /v1/identities/link
•	Entrada: { provider, external_id, token }
•	Lógica:
•	Valida token con API externa (ORCID/GitHub).
•	Crea o actualiza registro en Postgres.
•	Emite identity.linked.
•	GET /v1/identities/me
•	Devuelve identidades conectadas del actor actual.
Integración con Vault:
•	Leer secretos de cliente OAuth (client_id/secret) para cada proveedor desde vault: identity-service/oauth/*.
1.2. document-registry-service
Ya te di el esqueleto; lo resumo como servicio:
•	Endpoints:
•	POST /v1/documents – crea documento, version 1.
•	GET /v1/documents – lista por filtros (tenant, federación, estado).
•	POST /v1/documents/:uid/state – cambio de estado con validación de reglas y emisión de documents.state_changed.
•	Integra:
•	Postgres (documents y document_versions).
•	NATS (documents.* events).
•	security-core para firmar eventos críticos si así se diseña.
1.3. publication-service
Responsabilidad: orquestar publicaciones hacia GitHub, Zenodo, Figshare, OpenAIRE.
Endpoints:
•	POST /v1/publications
•	Entrada: { document_uid, providers[] }.
•	Lógica:
•	Valida estado del documento (consultando document-registry).
•	Aplica policy OPA (claims + RBAC + riesgo).
•	Crea registro en tabla publications (estado requested).
•	Emite publications.requested.
Workers internos (consumidores de eventos):
•	Consumidor de publications.requested:
•	Para cada provider:
•	Llama conector interno (p.ej. githubPublisher, zenodoPublisher).
•	Actualiza publications (estado completed/failed).
•	Emite publications.completed o publications.failed.
Integración con Vault:
•	Tokens de acceso a providers (patrones kv/data/publication/github, etc.).
1.4. federation-anchor-service
Responsabilidad: generar anclas de federación y comprobar consistencia entre F1–F7.
Consumidores:
•	documents.created, documents.versioned, publications.completed.
Lógica:
1.	Cuando recibe uno de esos eventos:
•	Calcula hashes por federación relevante.
•	Registra anclaje en DB (federation_anchors).
•	Emite federations.anchored.
2.	Job periódico:
•	Recorre anchors y compara hashes registrados por federados.
•	Emite federations.consistency_checked.
Opcional:
•	Anclaje externo (ej. escritura de hash en ledger externo) encapsulado aquí.
1.5. security-core (firma/verificación + Vault)
Responsabilidad: núcleo de seguridad: firma y verificación de eventos, rotación de claves, normalización de incidentes.
1.5.1. Integración con Vault
Se usa node-vault (o client moderno TS) para acceder a:
•	Ruta transit/ para firma/verificación.
•	Ruta kv/ para otros secretos.
Ejemplo de cliente:
ts
import vaultFactory from "node-vault";

const vault = vaultFactory({
  endpoint: process.env.VAULT_ADDR!,
  token: process.env.VAULT_TOKEN!
});

export async function signEvent(payload: object): Promise<string> {
  const serialized = JSON.stringify(payload);
  const res = await vault.write("transit/sign/atlas-events", {
    input: Buffer.from(serialized).toString("base64")
  });
  return res.data.signature; // ej: vault:v1:...
}

export async function verifyEvent(payload: object, signature: string): Promise<boolean> {
  const serialized = JSON.stringify(payload);
  const res = await vault.write("transit/verify/atlas-events", {
    input: Buffer.from(serialized).toString("base64"),
    signature
  });
  return res.data.valid === true;
}

3. CONSOLE ETERNITY – especificación funcional total
Ahora la parte divertida: la consola que le das al usuario, pero con disciplina de ingeniería y sin caer en juguete.
3.1. Concepto
CONSOLE ETERNITY es la consola soberana de programación y operación de ATLAS/TAMV:
•	Visualmente:
•	Marcos en azul metalizado.
•	Pantalla principal negra (dark mode), con tipografía de alta legibilidad.
•	Background tipo “matrix” platino (líneas/partículas discretas), sólo visible en ciertos estados de logro (sin errores, guardado exitoso, compilación limpia).
•	Funcionalmente:
•	Terminal + editor + visor de eventos + panel de estado en una misma experiencia unificada.
•	Conecta a todos los servicios: identidad, documentos, publicación, federador, seguridad, telemetría.
•	Exposición directa de comandos de alto nivel; es la “shell” del ecosistema.
3.2. Arquitectura técnica de la consola
•	Frontend:
•	React + TypeScript.
•	Terminal basada en xterm.js o similar con soporte para: streams, colores ANSI, output enriquecido.
•	Componente de editor (Monaco/CodeMirror) embebido.
•	Motor de temas (CSS variables / design tokens) con:
•	Paleta principal dark: fondo #050608–#101015, texto gris muy claro.
•	Borde azul metalizado (gradiente suave).
•	Efecto “matrix platino” (animación CSS/WebGL muy sutil, no distractora).
•	Backend de consola (parte de atlas-bff o servicio específico eternity-console-service):
•	WebSocket para comandos interactivos.
•	Proxy seguro hacia APIs internas (document-registry, publication, security-core, telemetry).
•	Control de permisos por comando (RBAC/OPA).
3.3. Modelo de comandos
Ejemplos de comandos de consola:
•	atlas status – estado general de servicios y federaciones.
•	atlas doc:new – crea documento nuevo.
•	atlas doc:open <document_uid> – abre documento en editor incrustado.
•	atlas doc:validate <document_uid> – valida estado, sintaxis, políticas.
•	atlas doc:publish <document_uid> --providers=github,zenodo.
•	atlas events:tail – stream de eventos en tiempo real.
•	atlas security:audit <document_uid> – muestra trail de auditoría.
3.4. Estados visuales y background Matrix platino
Estados principales:
1.	Normal (modo edición/trabajo)
•	Fondo negro puro, borde azul metalizado estático.
•	Sin matrix.
2.	Guardado/compilación exitosa
•	Se activa animación matriz platino durante 2–3 segundos:
•	Líneas verticales discretas en color platino suave (#E5E4E2) cayendo con baja opacidad.
•	Lanza sonido breve (1–2s) de “confirmación tecnológica” (archivo guardado / build ok).
3.	Corrección total de errores en archivos
•	Cuando el analizador detecta cero errores (lint, typecheck, validaciones de policy):
•	Matrix platino se activa durante más tiempo (p.ej. 5s) y se combina con un halo suave en el borde azul.
•	Sonido sutil de “éxito mayor” (pero sin ser gamification infantil).
4.	Errores críticos
•	Matrix desactivado (no se premia el estado roto).
•	Color de borde puede tornarse levemente ámbar/rojo en esquinas.
•	Sonido breve (1–2s) que indica error (no estridente, pero inequívoco).

2.1. Backend WebSocket sencillo (Node + ws)
ts
// services/eternity-console-service/src/wsServer.ts
import WebSocket, { WebSocketServer } from "ws";

type Client = {
  ws: WebSocket;
  userId: string;
};

const clients = new Map<string, Client>();

export function startWsServer(server: any) {
  const wss = new WebSocketServer({ server, path: "/eternity" });

  wss.on("connection", (ws, req) => {
    const userId = validateAndExtractUser(req); // JWT
    const clientId = `${userId}-${Date.now()}`;

    clients.set(clientId, { ws, userId });

    ws.on("message", (data) => handleMessage(clientId, data.toString()));
    ws.on("close", () => clients.delete(clientId));

    ws.send(JSON.stringify({ type: "event", event: "console.connected" }));
  });
}

async function handleMessage(clientId: string, raw: string) {
  const client = clients.get(clientId);
  if (!client) return;

  const msg = JSON.parse(raw);

  if (msg.type === "command") {
    client.ws.send(JSON.stringify({
      id: msg.id,
      type: "ack",
      status: "accepted"
    }));

    // Aquí mapeas comandos a handlers reales
    runCommand(client, msg).catch((err) => {
      client.ws.send(JSON.stringify({
        id: msg.id,
        type: "error",
        error: { code: "INTERNAL", message: err.message }
      }));
    });
  }
}

import { useEffect, useRef, useState } from "react";

export function useEternitySocket() {
  const socketRef = useRef<WebSocket | null>(null);
  const [connected, setConnected] = useState(false);

  useEffect(() => {
    const ws = new WebSocket("wss://bff.atlas/eternity?token=...");

    ws.onopen = () => setConnected(true);
    ws.onclose = () => setConnected(false);

    socketRef.current = ws;

    return () => {
      ws.close();
    };
  }, []);

  function sendCommand(command: string, args: any = {}) {
    const id = `req-${Date.now()}`;
    const msg = { id, type: "command", command, args };
    socketRef.current?.send(JSON.stringify(msg));
    return id;
  }

  return { connected, sendCommand, socket: socketRef.current };
}

        if (msg.type === "output") {

          if (msg.state === "error") playSound("build_fail");

  function handleKey(command: string) {
    const id = sendCommand(command);
    termRef.current?.writeln(`\r\n$ ${command} [${id}]`);
  }

  return (
    <div className="eternity-shell">
      <div id="eternity-terminal" />
    </div>
  );
}

Pseudo código consumidor:

async function handleEvent(msg: Msg) {
  const event = JSON.parse(sc.decode(msg.data));
  if (alreadyProcessed(event.event_id, SERVICE_NAME)) {
    msg.ack();
    return;
  }

  try {
    await processEvent(event);
    await markProcessed(event.event_id, SERVICE_NAME, "success");
    msg.ack();
  } catch (err) {
    await markProcessed(event.event_id, SERVICE_NAME, "failed", err.message);
    // publícalo a DLQ opcionalmente
    await nc.publish(`${event.event_type}.dlq`, msg.data);
    msg.ack();
  }
}

•	Mata uno de los pods de NATS -> comprueba que:
•	reconexión automática de clientes,
•	no hay pérdida irrecuperable de eventos.
•	Network latency entre servicios y NATS:
•	Verifica que los timeouts/retries están bien configurados.
Métricas a observar:
•	nats_server_connections, nats_server_in_msgs, nats_server_out_msgs.
5.2. Experimentos Postgres
•	Kill de primario en cluster HA:
•	Observa failover y tiempo de indisponibilidad.
•	CPU hog o I/O throttling:**
•	Mide latencia P95 de queries, tiempos de respuesta de servicios.
Resultados deben compararse con SLOs definidos.

6. Workflow de estados en la CONSOLE ETERNITY
Estados de alto nivel:
•	idle – esperando comandos.
•	running – ejecutando uno o más comandos.
•	clean – sin errores pendientes (últimos comandos = success).
•	error – últimos comandos con error.
•	matrix – modo visual especial cuando clean y se cumplen condiciones (p.ej. 0 errores en análisis de proyecto).
Transiciones:
•	idle -> running cuando se envía comando.
•	running -> success para un comando; si no hay otros en error → clean.
•	running -> error si un comando falla → estado global error.
•	clean -> matrix cuando se detecta:
•	análisis lint/typecheck success,
•	última acción = save/publish success,
•	se dispara evento console.matrix_enter.
Estado persistente:
•	Guardado en localStorage/IndexedDB:
•	lista de comandos recientes,
•	último estado matrix,
•	preferencias de sonidos/tema,
•	documentos recientes.

7. Integración de xterm.js con backend
Ya tienes el hook y el componente base:
•	xterm se usa sólo como capa de presentación encima de WebSocket.
•	Cada mensaje output → term.write.
•	Cada state → cambio de estado interno → UI + sonidos.
Para entrada de texto:
•	Cachas teclas en xterm y, al presionar Enter, parseas la línea y la traduces a command + args (comando Atlas).
•	Esta capa puede hacer autocompletado local (p.ej. lista de comandos conocidos).
